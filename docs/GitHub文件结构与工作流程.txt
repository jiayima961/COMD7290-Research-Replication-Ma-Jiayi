4. GitHub提交版本需有固定tag、具名Release和完整commit标识；Release附上与Moodle完全相同的报告。
5. 截止日期、课程成绩占比及平台另行说明的提交安排，以Moodle为准。

三、这些文件之间怎样联系

1. sources/：提供依据——论文和作者材料说了什么。
2. docs/：解释你的理解——为什么用这些变量、这些模型和这些判断规则。
3. data/：保存分析所需的输入。
4. analysis/：保存计算方法——程序怎样把数据变成结果。
5. tests/：检查输入和分析步骤是否符合已确认的规则。
6. outputs/：保存实际算出的结果和检查结论。
7. records/：说明谁做了什么、依据是什么、怎样核对和修改。
8. README.md：把上述内容连接起来，让老师能从每个假设找到说明、程序、结果和结论。
9. report/：用简短文字解释最重要的研究过程和发现，完整技术证据保存在项目中。

最重要的一条对应关系是：
理论和假设 -> 变量和模型 -> 数据和程序 -> 实际结果 -> 核验 -> 结论。
hypothesis_matrix.csv负责把这条关系逐项记录清楚。

四、文件准备时要注意什么

1. 文件夹中需要保存的内容，不一定都能上传GitHub。
   原始数据、整理数据、论文、作者代码和模型输出都要看许可和隐私限制。
   不能分享的内容可留在本地，并在README中写清楚合法获取方法和复现限制。

2. 至少三个技能包要实际使用并测试。
   每个SKILL.md要写名称和描述、输入、步骤、输出、检查方法和停止条件。
   至少一个技能专门处理所选论文的复杂模型或测量问题。
   要证明Codex能发现这些技能，明确调用过它们，并检查了实际输出。

3. 程序文件后缀要等选题后决定。
   可能使用R、Python、Mplus、Stata或MATLAB。不能默认所有论文都能直接用同一种软件完成。
   如更换原文的软件，需要说明统计分析与原方法等价。

4. 需要一个总运行入口。
   可以是主脚本或一条明确命令，让程序依次完成数据处理、分析和比较输出。
   必须测试从干净状态重跑，不能依赖聊天记录或交互式笔记本中没保存的状态。

5. 原文数值与本次计算结果分开存放。
   不要把作者已保存的参数当成本次重新拟合的结果。
   小规模试跑也要与正式完整运行分开标记。

五、接下来的工作流程

第1步：比较六篇论文，选定一篇
查看研究主题是否有兴趣，数据和材料能否获取，软件、许可和运行时间是否允许。
清点论文中所有研究、表、图、模型和相关补充分析，不能只选择最简单的部分。
产出：选题决定、完整材料和分析清单、缺失问题清单。

第2步：建立项目和GitHub访问
创建个人私有仓库；作业要求开始时邀请老师fffchaobu，但按你当前的明确要求暂不邀请，后续另行办理并检查访问。
建立基本目录，写README.md、AGENTS.md、STATUS.md和材料来源记录。
完成软件与权限检查，以及一个小规模、已获允许的执行测试。
产出：老师可以访问且入口清楚的项目；记录检查点A“可行性”。

第3步：先把论文的道理讲明白
阅读论文、补充材料、编码说明及其引用的至少两项基础理论或方法文献。
你先自己写：作者想回答什么问题、为什么提出这些假设、准备怎样验证。
再请Codex帮助核对和修订，并保留来源页码、章节或代码位置。
区分作者写明的决定、你的理解和你的批评；探索性问题不能改成事先假设。
有预注册时，要与发表版本比较；本次事后制定的复现计划不是原始预注册。
产出：理论说明、初步理论图、假设与分析对应说明。

第4步：明确变量、样本和模型，并由你确认
说明一行数据代表什么，如何选样本，变量怎样计分，缺失值怎样处理。
把具体模型、软件设置、判断规则和检查方法写清楚，补齐假设对应表和模型图。
你理解并确认后，再进入正式估计。
产出：明确、带版本的分析方案；记录检查点B“分析方案”。

第5步：建立三个技能包，安排协作与交接
分开安排四种职能：理论和模型审查、数据和测量分析、模型实现、复现核验。
可用不同会话或子代理，不要求同时运行，也不要求购买多个平台账号。
每个任务要写输入、来源、版本、权限、预期输出、检查和停止条件。
完成后交代改了什么、运行了什么、得到了什么、还有什么问题。
至少成功演示一次新会话仅凭项目文件继续工作。
产出：实际调用过的技能、任务和交接记录。

第6步：整理数据，先核对基本结果
保留作者数据原样，通过程序完成筛选、合并、编码、计分和分析样本生成。
先检查样本人数、缺失、变量取值，再计算描述统计。
只拿到整理后数据时，明确从该数据开始，不声称完成了看不到的原始数据处理。
产出：整理程序、检查结果、描述统计及数据版本记录。

第7步：先小规模试跑，再运行正式模型
用小规模运行排查语法、软件和资源问题，检查后再完成正式完整拟合。
保留论文要求的复杂模型，覆盖各研究及相关补充分析。
作者代码可以使用，但要注明来源，并解释关键部分对应哪个假设和输出。
保存版本、命令、时间、随机种子、结果和适用的模型诊断。
材料和代码互相矛盾时，记录冲突并说明采用哪一版作为忠实复现目标。
产出：真正重新运行得到的结果及完整日志。

第8步：检查结果，而不仅是看程序有没有报错
编写针对样本、变量、合并、时间顺序及模型要求的检查。
完成至少一次无害的负向测试：在副本或模拟数据中故意加入错误，证明程序能发现；随后恢复并重跑。
通过另外实现的计算或方法，核验至少一个重要描述统计量和一个核心复杂模型量。
换一个AI会话评价、重跑同一份作者代码，都不等于独立统计核验。
审查至少三个重要AI决定，记录来源依据、你接受或修改的决定及影响，不必人为制造错误。
产出：测试、诊断、独立计算、审查报告和差异记录；记录检查点C“执行与审计”。

第9步：逐项比较并解释
制作原文结果与本次结果比较表，写清差值、允许误差和原因。
把每项清单内容标为“已复现”“已复现但有差异”或“现有材料无法核验”。
解释效应大小、不确定性、竞争解释和局限。
区分数值一致、支持某个预测、支持某种机制、支持更广泛理论这四种说法。
说明实际发现的问题影响结论、估计还是报告透明度；无法完成的部分不能从清单中消失。
产出：结果比较表、覆盖清单、理论解释和局限说明。

第10步：完成自己的延伸分析和后续设计
忠实复现后，另做一次有理由的敏感性分析：改变一个设定，检查结论是否稳定。
说明分析目标或研究问题是否随之变化，与作者原分析分开报告。
写一页后续研究设计，包含新问题、新假设、设计、测量、样本量或精度依据、分析和解释规则。
这一步不要求收集新数据。
产出：敏感性分析程序与结果、一页后续研究方案。

第11步：重跑、写报告、固定版本并提交
从干净状态测试总运行命令，检查README能否带老师找到并重建结果。
完成1,000–1,200 words个人报告，按APA第七版排版。
访问信息块写姓名、学号、所选论文、仓库完整网址、协作者邀请状态、Release/tag和完整commit标识。
创建固定tag和具名GitHub Release，附上与Moodle相同的报告。
你亲自检查复杂模型结果、项目访问和提交清单，记录最终决定。
提交后保留tag，之后的修正单独记录。
产出：最终GitHub版本、Moodle报告；记录检查点D“完成”。

第12步：准备个人答辩
练习讲清一项结果如何从理论一路走到假设、变量、模型、程序、输出和结论。
准备解释：如果测量方式、样本结构或设计条件变化，分析应怎样调整。
答辩需要你本人理解和回答。

六、最低数量要求速查

- 从六篇论文中选一篇，覆盖该论文全部研究和相关补充分析。
- 阅读论文引用的至少两项基础理论或方法文献。
- 至少三个项目级技能包，至少一个针对所选论文的复杂问题；都要实际调用和检查。
- 四种工作职能分开安排。
- 至少一次成功的新会话交接。
- 至少一次故意加入错误的无害测试。
- 独立核验至少一个重要描述统计量和一个核心复杂模型量。
- 审查至少三个重要AI决定。
- 一次有理由的敏感性分析。
- 一页后续研究设计。
- 一条经过干净重跑测试的总运行命令。
- 四个带日期的阶段检查点，它们不是四轮额外提交。
- 最终报告、固定tag、具名Release和完整commit标识。

七、特殊情况和可选项

1. 选内容分析论文时，必须用原始独立编码员评分复现信度，不能用协商后的共识编码代替。
   还要区分新闻条目、行动者和行动者提及单位，复现有序模型、多层逻辑回归、概率摘要和边际效应。
   用AI重新编码原文是可选扩展，需有合法文本访问，不能替代原始信度复现。

2. MCP、Superpowers、持续集成和同时运行多个代理都不是必需项。
   不要求制作网站、应用或产品原型，也不要求招募新样本。

3. 报告按APA第七版排版：12磅Times New Roman、黑字、一英寸页边距、正文双倍行距、
   首行缩进0.5英寸、页码、作者—年份引文及悬挂缩进参考文献。
   图表编号并命名；表格少量横线、不用竖线；DOI和网址完整显示。
   报告文件格式和其他未明确事项以课程平台说明为准。

4. 评分重点是研究理解、测量和模型是否匹配、受控AI协作、完整复现、独立核验、
   模型图、透明的局限说明，以及你解释和运用研究逻辑的能力。
